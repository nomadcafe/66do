# 分期出售与年度指标（备忘）

> 记录讨论结论，便于后续决定是否开发与如何排期。非实施说明。

## 背景问题

- **Annual Sales / Annual Net Profit（Overview）** 当前 largely 依赖：卖出交易的 **`date` 所在日历年** + 单条 `sell` 上的金额（分期时在 `transactionsForMetrics` 中会按 **已付期数** 折成「截至目前实际已收」）。
- **一条分期合同 = 一条 `domain_transactions` 记录**，用 `paid_periods`、`installment_period` 等表达进度。
- 因此：**按「自然年 / 实际到账年」拆分分期收款** 与 **单条记录 + 单一 `date`** 存在张力；年度净利里还有 **按卖出条数摊总持有成本** 的简化，与真实「本年赚多少」不一定一致。

## 当前行为（摘要）

- 年度筛选：`transaction.date` 的年份 = 当前日历时，该条 `sell` 计入当年年度销售/年度净收入侧（见 `enhancedFinancialMetrics.ts`）。
- 分期未结清：金额侧多为 **首付 + 已付期数 × 每期**（与表单/指标一致），但 **仍挂在这一条交易的 `date` 年**，不会自动把各期拆到不同历年。
- 若补录时把 `date` 填成「录入日」，可能出现 **多个月已收现金在年度上全挤进一年** 的观感。

## 可选方向（由轻到重）

1. **维持一条分期 + 只调 `paid_periods`**  
   - 优点：实现简单、列表干净。  
   - 缺点：年度按「到账年」不精确；依赖用户 **`date` 填法**。

2. **年度改为「现金口径」汇总（不改表结构）**  
   - 本年流入 − 本年流出（各类型交易按 `date` 过滤）。  
   - 分期仍一条时：**跨年现金**仍不完美，除非配合下面 3 或 4。

3. **合同上增加辅助字段 + 算法按「月起算」估算已收落在哪些年**  
   - 仅用于年度展示，需标注「估算」；不规则付款会有误差。

4. **分期子收款表（或等价结构）——父记录 = 合同，子记录 = `{ date, amount, net? }`**  
   - **年度** = 子记录按 `date` 年求和。  
   - **总已收** = `sum(子)`，可与 `paid_periods` 互校或以后以子表为准。  
   - **优点**：跨年、对账、导出、报税场景下**结构最清晰、长期最不易推翻**。  
   - **缺点**：库表、API、UI、与现有指标/报表的衔接 **工作量最大**。  
   - **折中**：子收款 **可选**——无子记录时回退 `paid_periods`；有子记录时年度/已收以子表为准。

## 结论倾向（供决策）

- 若产品目标包含 **按自然年对账、跨年分期、与流水一致**：**子收款表是长期最优解**；是否「全用户强制」可再议，**可选子表 + 旧数据回退** 可降低迁移压力。  
- 若多数用户不分期、不抠年度：**一条 + `paid_periods` + 文案说明限制** 可能足够。

## 若后续实施子表，需提前想清楚

- 父合同总价、手续费与子行 **是否允许差额、如何校验**。  
- 与现有 **出售后域名状态、分享图、ROI** 等是否 **以父合同 + 子收款汇总** 为准。  
- 历史数据 **迁移策略**（仅新数据 / 批量导入脚本）。
